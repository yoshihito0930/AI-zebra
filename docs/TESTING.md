# Testing

このリポジトリでの、テストと制御の考え方。
関連：[core-beliefs.md](design-docs/core-beliefs.md)（不変条件と自律度）

## 基本の考え方

- **仕様は自然言語、テストはコード。** 仕様（product-specs）は人間が自然言語と具体例で書く。テストはそれを実行できる形にしたもの
- **テストは実装より先に、仕様だけから書く。** 実装を見て書いたテストは、実装をなぞるだけになり、制御として効かない
- **テストを書くエージェントと、実装するエージェントを分ける。** 自分の作業を自分で採点しない
- **人間がレビューするのは、まずテスト。** テストが仕様どおりなら、実装はテストとCIに任せられる

## 進め方

自律度「中」の領域（空き判定、予約の作成・変更・取消、公開APIの契約など）では、必ずこの順で進める。
自律度「高」の領域では、実装と同じPRでテストを書いてよい。

1. **仕様を書く（人間）**
   product-specs に、ルールと具体例を書く。曖昧な点は「未決事項」に残す
2. **テストのPRを作る（テスト担当のエージェント `test-writer`）**
   仕様と契約（packages/contracts）だけを読んでテストを書く。既存の実装は読まない・変えない。依存（package.json）も変えない。テストに新しい依存や契約（packages/contracts）のスキーマが要るときは、テストの PR の前に、人間かテスト担当以外が準備の PR を出す。仕様が曖昧で書けない箇所は、推測せず未決事項に追記して止まる。PRには次を入れる
   - テスト（例の節ごとに `describe`）
   - スタブ：テストが呼ぶ関数の形（名前・引数・戻り値の型）だけを決め、中身は「未実装」のエラーを投げる新しいファイル。型チェックを通すため
   - 失敗予定リスト（`harness/expected-failures.txt`）への、足したテストファイルの追加
   - 例の網羅の保留リスト（`harness/spec-coverage-pending.txt`）からの、テストを書いた節の削除
3. **テストをレビューしてマージする（人間）**
   テストが仕様を正しく表しているか、スタブの形（関数の名前・引数・戻り値）が妥当かを確認してマージする。テストは失敗予定リストに入っているので、必須のチェックは通る
4. **実装のPRを作る（実装担当のエージェント `implementer`）**
   スタブの中身を実装してテストを通し、失敗予定リストからその行を消す。**既存のテストは変更しない**
5. **テストの方が間違っていると判断したら**
   実装担当はテストを直さず、理由を書いて人間に質問する。直す場合は、テストだけを直すPR（人間がレビュー）を先に出す

テストの形（関数の名前・引数・戻り値）はテストのPRで決まる。実装担当は、その形に合わせて実装する。

エージェントの定義は `.claude/agents/`（`test-writer.md`、`implementer.md`）。それぞれのエージェントが役割の外の操作（実装担当がテストを変える、テスト担当が main にある実装を読む・変える。テスト担当がそのブランチで作ったスタブは除く）をしようとしたら、フック（`scripts/harness/src/agent-guard.js`）が止める。ただし、シェル経由の回り道（スクリプトの中でファイルを開く、パスを引用符で囲むなど）までは止められない。最後の歯止めは、下の CI のチェックと人間のレビュー。
フックは、フォルダーが未信頼のときなどに黙って外れることがある。そのため、どちらのエージェントも作業の最初に、通っても害のない禁止の操作を試してフックが効いていることを確かめ、効いていなければ何もせずに止まる。

## 仕様の例とテストの対応づけ

仕様の例には番号を振らない。見出しと行の内容で対応づける。

- 仕様の書き方：例の表は、「例」という見出しの下に置く。「例」の見出しの親（1つ上の階層の見出し）が、その例の節の名前になる。たとえば「## 料金」の下に「### 単価」「### 計算」「### 例」と並んでいるとき、節の名前は「料金」
- テストの書き方：`describe` の名前に節の名前（例：「申込の締め切り」）を、`it` の名前に例の行の内容（入力と結果）をそのまま書く
- CI：product-specs の「例」の見出しの節の名前が、どこかのテストの `describe` に出てくるかを確かめる。出てこない節があれば失敗させる（`pnpm spec-coverage`）
- まだテストを書いていない節は、`harness/spec-coverage-pending.txt`（保留リスト）に書いておけば失敗にしない。テストができたのに保留リストに残っている節と、仕様にない節が保留リストにあるときも失敗させる
- JST で判定する関数（INV-7。利用日、深夜帯、仮予約の期限、キャンセル料の日数など）のテストでは、例の各行を、同じ時点の UTC に直した入力でも同じ結果になることも確かめる。期待値は例の行のままなので、仕様に行を足さなくてよい。入力のゾーンの日付や時刻をそのまま使う誤り（DB から読んだ UTC の日時を渡すと、利用日や期限が1日ずれる）を止めるため
- 節の中の行がすべてテストになっているかは、テストのレビュー（人間）で確かめる

理由：仕様は人間が自然言語で読みやすく書いたままにし、節の抜けだけは機械で見つける。表をテストが直接読む方法は、自然言語の結果を解析する必要があり、壊れやすい。

### 例

booking.md の「申込の締め切り」の節の例の表に「10/13 18:00 ／ 本予約申込：受付 ／ 仮予約申込：不可（期限を過ぎた）」という行がある場合。

```ts
describe("申込の締め切り", () => {
  it("開始 10/20 15:00、申込 10/13 18:00：本予約申込は受付、仮予約申込は不可（期限を過ぎた）", () => {
    // ...
  });
});
```

| 状況 | CIの結果 |
|---|---|
| booking.md の「例」の見出しがある節がすべて、テストの `describe` に出てくる | 成功 |
| booking.md に「予約の変更」の例を足したが、`describe("予約の変更", ...)` がない | 失敗 |

## 実装PRでテストを変更させない

- 実装を含むPRで、**既存の**自律度「中」の領域のテストファイルが変更・削除されていたら、CIで失敗させる（`pnpm test-tamper`）。新しいテストを足すことは止めない（テストのPRがスタブと一緒に足すため）
- 実装ファイルは、`apps/`・`packages/`・`tooling/`・`scripts/` の下のコード（テスト以外）
- 失敗予定リストに足した項目が、そのPRで新しく足したテストでなければ、CIで失敗させる。レビュー済みのテストを失敗予定にして隠せないようにする
- 失敗予定リストのテストは、本当にまだ失敗するかをCIで確かめる（`pnpm expected-failures`）。通るようになったのにリストに残っていたら失敗させる
- テストの置き場所：対象のファイルの隣に `*.test.ts`（統合テストは `*.int.test.ts`）
- どのパスが自律度「中」の領域かは `harness/autonomy.json` に glob で書く。このファイルの変更も自律度「中」
- 自律度「中」の領域の範囲（`harness/autonomy.json`）は、PR側ではなく比較元（main）のものを読む。PRの中で範囲を書き換えて、チェックをすり抜けられないようにするため

| PRの中身 | CIの結果 |
|---|---|
| 新しいテスト、スタブ、失敗予定リストへの追加（テストのPR） | 成功（人間がレビュー） |
| 実装と、失敗予定リストからの削除（実装のPR） | 成功 |
| 実装したが、失敗予定リストから消し忘れた | 失敗（`expected-failures`） |
| 既存の自律度「中」のテストの変更と、実装 | 失敗 |
| 既存の自律度「中」のテストの削除と、実装 | 失敗 |
| 実装と、既存のテストを失敗予定リストに追加 | 失敗 |
| 既存の自律度「中」のテストの変更だけ（テストを直すPR） | 成功（人間がレビュー） |
| 自律度「高」の領域のテストと実装の両方 | 成功 |
| 既存のテストと仕様（docs）を一緒に直す | 成功（人間がレビュー） |

## テストの種類

| 種類 | 何を確かめるか | 主な対象 |
|---|---|---|
| 単体テスト | 関数・モジュールが仕様どおりに振る舞うか | 空き判定、区間計算、バリデーション、料金・キャンセル料の計算（INV-9）、日時の境界（INV-7） |
| プロパティベーステスト | どんな入力でも不変条件が崩れないか | INV-1（ダブルブッキング禁止） |
| 統合テスト | DBを含めて正しく動くか | INV-2（トランザクション）、INV-6（承認されていない下書きは送れない）、INV-10（ログと通知に個人情報が出ない）、Googleカレンダーの取り込み（Google の API はモックにする）。ローカルのDynamoDBで実行 |
| 契約テスト | APIの入出力がスキーマどおりか、余計な情報を返していないか | 公開API（INV-3） |
| E2Eテスト | お客様・管理者の操作が通しで動くか | 申込 → 承認 → 確認メール下書き |
| ビジュアルリグレッション | 見た目が意図せず変わっていないか | ウィジェット、HP（デザイン決定後に導入） |

### ダブルブッキング（INV-1）は例だけで確かめない

エージェントが選ぶ例は、通りやすいケースに偏ることがある。
仕様の例を単体テストにするのに加えて、ランダムな操作の列を大量に生成し、「どの組み合わせでも、承認待ち・仮予約・本予約・第二キープの占有区間とブロック枠が、第二キープと仮予約1件の組を除いて重ならない。仮予約1件に重なる第二キープは1件まで」ことをプロパティベーステスト（fast-check など）で確かめる。
操作の列には、各種の申込（仮予約・本予約・第二キープ）、承認、却下、取消、仮予約の昇格、予約の変更（第二キープ付きの仮予約の移動を含む）、第二キープの繰り上げ・取消・終了、バッファの切り替え、ブロック枠の追加・更新・削除（Googleカレンダーの取り込みを含む）を含める。

## テスト以外の制御

テストは制御の一部。機械で判定できるものは、なるべくテストより前の層で止める。

| 層 | 何を止めるか |
|---|---|
| 型・Zod | データの形の間違い（INV-4） |
| lint | 依存の方向（INV-5）、SESを呼べるモジュールの限定（INV-6）、日時の扱い（INV-7）、金額の型（INV-9）、ロガーに渡せる型（INV-10）、禁止パターン |
| Terraformのポリシーチェック | コストを増やす構成（INV-8） |
| テスト | 振る舞いの間違い |
| エージェントによるレビュー | 機械で判定できないもの（UIの使いやすさ、メールの文面など）。観点リストを自然言語で渡して評価させる。観点リストは `docs/review-checklists/` に、観点ごとに1ファイルで置く（必要になったときに作る） |
| 人間のレビュー | 自律度「中」「低」の判断 |

ドキュメントに書いても守られないルールは、lintかテストに昇格させる。昇格したら [harness-log.md](harness-log.md) に記録する。

## テストが書けるための前提

- すべてのテストは、AWSに接続せずローカルで実行できる
- 1つのコマンドでテスト一式が実行できる
- 日時に依存するテストは、現在時刻を固定して実行する

## 未決事項

なし

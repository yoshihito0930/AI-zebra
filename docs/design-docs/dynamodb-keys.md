# DynamoDB のキー設計

予約・ブロック枠・履歴を、DynamoDB にどう置き、どう読み書きするか。キー設計の変更は自律度「低」（[TECH_STACK.md](../TECH_STACK.md)）。

関連：[reservation-model.md](reservation-model.md)（予約が持つもの、操作）、[core-beliefs.md](core-beliefs.md)（INV-1、INV-2、INV-3、INV-7、INV-10）

## 決めたこと

- テーブルは1つ。キーは `pk`（パーティションキー）と `sk`（ソートキー）の文字列
- 重なりは、**日ごとのアイテムと版番号**で止める。30分ごとの枠のアイテムは持たない
- お客様の個人情報は、予約のアイテムとは別のアイテムに置く

理由：日ごとのアイテムなら、24時間を超えるブロック枠もトランザクションに収まり、第二キープの決まりも booking-core の判定をそのまま使える。空き状況を読むときのアイテムの数も少ない。個人情報を分けると、保存期間が決まったときに個人情報だけを消せ、一覧や空き状況を読むときに個人情報を読まずに済む（INV-10）。

## アイテム

| 種類 | pk | sk | 中身 |
|---|---|---|---|
| 予約 | `RES#<予約の id>` | `META` | 状態、予約区間、バッファ、経路、人数、ホリゾントの養生、プランの id、機材保険、オプション、見積額、確定金額、第二キープの仮予約の id、作成日時、更新日時 |
| 予約の個人情報 | `RES#<予約の id>` | `PII` | 氏名、会社名、メールアドレス、電話番号、住所、カメラマン氏名、撮影内容、撮影詳細、補足事項 |
| 履歴 | `RES#<予約の id>` | `HIST#<日時（UTC）>#<連番>` | 誰が、操作、変更の前後（reservation-model.md「履歴」。個人情報は項目名だけ） |
| ブロック枠 | `BLK#<ブロック枠の id>` | `META` | 区間、バッファ、経路（管理者／Googleカレンダー）、理由のメモ |
| 日ごと | `DAY#<JST の日付 YYYY-MM-DD>` | `META` | 版番号と、その日にかかる占有区間の一覧 |

- 日時は UTC の ISO 8601 で保存する（INV-7）。日ごとのアイテムの日付だけは JST で区切る（利用日と管理画面のカレンダーが JST のため）
- Googleカレンダーから取り込んだブロック枠の id は、イベントの id から決める（`gcal-<イベントの id>`）。取り込み直しで同じブロック枠を見つけられるようにするため
- 日ごとのアイテムの占有区間の一覧の1件は、種類（予約／ブロック枠）、id、予約なら状態と第二キープの仮予約の id、占有区間の開始と終わり。booking-core の判定に要るものだけを持ち、個人情報は持たない
- 日ごとのアイテムには予約の状態も入るが、公開APIは「空き／第二キープ可／空きなし」に直してから返す（INV-3）

## 書き込み（INV-1、INV-2）

枠を確保・解放するどの操作も、次の手順で行う。

1. 操作にかかわる日（変更前と変更後の占有区間がかかる JST の日）の日ごとのアイテムを、強い整合性で読む
2. 読んだ占有区間から booking-core の関数の入力を組み立て、判定する（`checkAvailability`、`checkSecondHoldApplication`、`applyReservationOperation`、`applyReservationChange` など）。不可ならここで終わる
3. `TransactWriteItems` で、日ごとのアイテム（条件：版番号が読んだときと同じ。まだないなら、まだないこと）、予約（またはブロック枠）、個人情報（申込のとき）、履歴をまとめて書く
4. 条件で失敗したら（同じ日に別の書き込みがあった）、1 からやり直す。回数に上限を設け、超えたら「混み合っている」としてエラーにする

- 同時に2件の申込が同じ時間に来ても、先に書いたほうの版番号の更新で、後のほうのトランザクションは失敗する。後のほうは読み直して判定し、重なっていれば不可になる
- アイテムの数：最長の予約の占有区間（25時間）は JST の日を最大3つまたぐ。変更は変更前と変更後で最大6日分と、予約・履歴で8アイテム。ブロック枠は N 日なら N+1 アイテムほど。`TransactWriteItems` の上限（100アイテム）に収まるのは、およそ95日までのブロック枠
- 重なりの正しさは booking-core の判定に頼る。DB は「読んだあとに誰も書いていない」ことだけを保証する。INV-1 は、booking-core のプロパティベーステストと、DB を使う統合テスト（同じ時間への同時の申込で、片方だけが成功すること）で確かめる

## 読み出し

| 使う所 | 読むもの |
|---|---|
| ウィジェットの空き状況 | 期間の日ごとのアイテム（1か月で約31件）を BatchGet。booking-core で「空き／第二キープ可／空きなし」に直す。予約や個人情報は読まない |
| 管理画面のカレンダー | 期間の日ごとのアイテムと、そこに出てくる予約の `META` を BatchGet。個人情報は、予約を開いたときだけ読む |
| 予約の詳細 | `RES#<id>` を Query（`META`、`PII`、履歴） |
| 承認待ちの一覧、期限の警告 | 予約の `META` に GSI を付ける（`gsi1pk` = `STATUS#<状態>`、`gsi1sk` = 開始日時）。取消・終了は GSI に入れない（属性を消す） |
| Googleカレンダーの取り込み | ブロック枠の id がイベントの id から決まるので、`BLK#gcal-<イベントの id>` を直接読む |

## まだ決めていないこと

- 取消・終了した予約と、個人情報・履歴を残す期間（booking.md の未決事項）。決まったら、個人情報のアイテムに TTL を付けるなどで消す
- 95日を超えるブロック枠を入れるか（長期の休業など）。入れるなら、分けて登録するか、日ごとのアイテムの持ち方を見直す

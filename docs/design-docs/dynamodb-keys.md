# DynamoDB のキー設計

予約・ブロック枠・履歴を、DynamoDB にどう置き、どう読み書きするか。キー設計の変更は自律度「低」（[TECH_STACK.md](../TECH_STACK.md)）。

関連：[reservation-model.md](reservation-model.md)（予約が持つもの、操作）、[core-beliefs.md](core-beliefs.md)（INV-1、INV-2、INV-3、INV-7、INV-10）

## 決めたこと

- テーブルは1つ。キーは `pk`（パーティションキー）と `sk`（ソートキー）の文字列
- 重なりは、**日ごとのアイテムと版番号**で止める。30分ごとの枠のアイテムは持たない
- お客様の個人情報は、予約のアイテムとは別のアイテムに置く

理由：日ごとのアイテムなら、24時間を超えるブロック枠もトランザクションに収まり、第二キープの決まりも booking-core の判定をそのまま使える。空き状況を読むときのアイテムの数も少ない。個人情報を分けると、保存期間が決まったときに個人情報だけを消せ、一覧や空き状況を読むときに個人情報を読まずに済む（INV-10）。

## アイテム

| 種類 | pk | sk | 中身 |
|---|---|---|---|
| 予約 | `RES#<予約の id>` | `META` | 状態、予約区間、バッファ、経路、受付番号（フォームの申込だけ）、人数、ホリゾントの養生、プランの id、機材保険、オプション、見積額、確定金額、第二キープの仮予約の id、作成日時、更新日時 |
| 受付番号 | `RCPT#<受付番号>` | `META` | 予約の id。受付番号は、紛らわしい文字（0・O・1・I）を除いた英大文字と数字の8文字（電話で読み上げても間違えにくくするため）。申込と同じトランザクションで、ないことを条件に作る（受付番号が重ならないことを DB で保証する）。既存の番号と重なったら、お客様の申込を断らずに別の番号を作り直してやり直し、やり直しの上限を超えたら「混み合っている」とする |
| 予約の個人情報 | `RES#<予約の id>` | `PII` | 氏名、会社名、メールアドレス、電話番号、住所、カメラマン氏名、撮影内容、撮影詳細、補足事項 |
| 履歴 | `RES#<予約の id>` | `HIST#<日時（UTC）>#<連番>` | 誰が、操作、変更の前後（reservation-model.md「履歴」。個人情報は項目名だけ） |
| 下書き | `RES#<あて先の予約の id>` | `DRAFT#<日時（UTC）>#<連番>` | 種類（承認・却下・昇格・取消・変更・第二キープの終了・繰り上げの案内・前倒しの案内など）、差し込む値（確定金額、キャンセル料、残っている仮予約の id など）、状態（未送信／送信済み／送らない）、作った操作 |
| ブロック枠 | `BLK#<ブロック枠の id>` | `META` | 区間、バッファ、経路（管理者／Googleカレンダー）、理由のメモ |
| 日ごと | `DAY#<JST の日付 YYYY-MM-DD>` | `META` | 版番号と、その日にかかる占有区間の一覧 |

- 日時は UTC の ISO 8601 で保存する（INV-7）。日ごとのアイテムの日付だけは JST で区切る（利用日と管理画面のカレンダーが JST のため）
- 下書きは、作った操作と同じトランザクションで書く（操作だけが残って下書きがない、を起こさないため）。文面は持たず、管理画面で開いたときにテンプレートから作る。お客様へ送るのは、管理者が確認してから（INV-6）。個人情報（あて先のメールアドレスなど）は持たず、送るときに個人情報のアイテムから読む
- Googleカレンダーから取り込んだブロック枠の id は、イベントの id から決める（`gcal-<イベントの id>`）。取り込み直しで同じブロック枠を見つけられるようにするため
- 日ごとのアイテムの属性：
  - `version`（数値）：版番号。書くたびに1増やす。アイテムがまだないときは、ないことを条件に作る（版番号は1から）
  - `intervals`（リスト）：その日にかかる占有区間の一覧。1件は次のマップ
    - `kind`：`"reservation"` か `"block"`
    - `id`：予約かブロック枠の id
    - `status`：予約なら `ReservationStatus`（ブロック枠にはない）
    - `provisionalIds`：第二キープ（承認待ちを含む）なら、付く仮予約の id のリスト（ほかにはない）
    - `start`、`end`：占有区間（バッファ込み）の開始と終わり。UTC の ISO 8601
    - `bufferMinutes`：バッファの長さ（予約は30か60、ブロック枠は0・30・60）。公開APIで予約区間（`end` − バッファ）を返すのに使う
  - 1つの占有区間が日をまたぐときは、かかる日それぞれのアイテムに、同じ区間（切らずにそのまま）を入れる
  - booking-core の判定に要るものだけを持ち、個人情報は持たない
- 日ごとのアイテムには予約の状態も入るが、公開APIは「表示名（仮予約／本予約／第二キープ／予約不可）と時間（予約区間）」に直してから返す（INV-3）。承認待ちかどうか・id は返さない

## 書き込み（INV-1、INV-2）

枠を確保・解放するどの操作も、次の手順で行う。

1. 操作にかかわる日（変更前と変更後の占有区間がかかる JST の日）の日ごとのアイテムを、強い整合性で読む
2. 読んだ占有区間から booking-core の関数の入力を組み立て、判定する（`checkAvailability`、`checkSecondHoldApplication`、`applyReservationOperation`、`applyReservationChange` など）。不可ならここで終わる。保存の層（apps/api/src/db）が判定するのは重なり（INV-1）と状態の移り変わりだけ。申込の締め切り・時間の単位・料金の計算など、申込の中身の検証は、その前に API の層で行う
3. `TransactWriteItems` で、日ごとのアイテム（条件：版番号が読んだときと同じ。まだないなら、まだないこと）、予約（またはブロック枠）、個人情報（申込のとき）、履歴をまとめて書く
4. 条件で失敗したら（同じ日に別の書き込みがあった）、1 からやり直す。回数に上限を設け、超えたら「混み合っている」としてエラーにする

- 現在時刻（作成日時・履歴の日時）は、保存の関数の引数で受け取る（Luxon の `DateTime`。INV-7。時計の部品 packages/clock の形は、API の層を作るときに決める）

- 同時に2件の申込が同じ時間に来ても、先に書いたほうの版番号の更新で、後のほうのトランザクションは失敗する。後のほうは読み直して判定し、重なっていれば不可になる
- アイテムの数：最長の予約の占有区間（25時間）は JST の日を最大3つまたぐ。変更は変更前と変更後で最大6日分と、予約・履歴で8アイテム。ブロック枠は N 日なら N+1 アイテムほど。`TransactWriteItems` の上限（100アイテム）に収まるのは、およそ95日までのブロック枠
- ブロック枠は、占有区間がかかる日を90日までにする（booking.md「ブロック枠のバッファ」）。直すときは、直す前と直したあとのかかる日を合わせて90日まで（両方にかかる日は1日と数える。「ブロック枠を消す・直す」）。95日を超えるブロック枠は入れない（長期の休業は分けて入れる）
- 重なりの正しさは booking-core の判定に頼る。DB は「読んだあとに誰も書いていない」ことだけを保証する。INV-1 は、booking-core のプロパティベーステストと、DB を使う統合テスト（同じ時間への同時の申込で、片方だけが成功すること）で確かめる

## 読み出し

| 使う所 | 読むもの |
|---|---|
| ウィジェットの予約状況（公開API） | 期間の日ごとのアイテム（1か月で約31件）を BatchGet し、表示名と予約区間に直す。予約の META や個人情報は読まない |
| 管理画面のカレンダー | 期間の日ごとのアイテムと、そこに出てくる予約の `META` を BatchGet。個人情報は、予約を開いたときだけ読む |
| 予約の詳細 | `RES#<id>` を Query（`META`、`PII`、履歴） |
| 受付番号から予約を探す（お客様からの問い合わせ） | `RCPT#<受付番号>` を読み、予約の id を得る |
| 未送信の下書きの一覧 | 下書きに GSI を付ける（`gsi1pk` = `DRAFT#UNSENT`、`gsi1sk` = 作った日時）。送信済み・送らないにしたら GSI の属性を消す |
| 承認待ちの一覧、期限の警告 | 予約の `META` に GSI を付ける（`gsi1pk` = `STATUS#<状態>`、`gsi1sk` = 開始日時）。取消・終了は GSI に入れない（属性を消す） |
| Googleカレンダーの取り込み | ブロック枠の id がイベントの id から決まるので、`BLK#gcal-<イベントの id>` を直接読む |

## まだ決めていないこと

- 取消・終了した予約と、個人情報・履歴を残す期間（booking.md の未決事項）。決まったら、個人情報のアイテムに TTL を付けるなどで消す

# Core Beliefs

このリポジトリで常に守る原則。ここに反する変更はマージしない。
ドキュメントで守れないルールは、lint・テスト・CIに昇格させる。

## このプロジェクトの目的

1. **スタジオゼブラで確実に運用を始める** — 実際のお客様の予約を、取りこぼしなく扱えること
2. **AIを主軸にした開発スタイルを試行錯誤する** — 人間は意図とハーネスを書き、コードはエージェントが書く

この2つがぶつかるときは、**本番のお客様に影響する部分では1を優先**する。それ以外では2を優先し、スピードを取る。

## 不変条件

| ID | 内容 | 強制手段 |
|---|---|---|
| INV-1 | **ダブルブッキング禁止。** 承認待ち・仮予約・本予約・第二キープの占有区間（予約区間の後ろのバッファ込み。原則1時間、管理者が予約ごとに30分に縮められる）とブロック枠の占有区間（ブロック枠の後ろのバッファ込み）は、互いに重ならない。例外として、第二キープは承認済みの仮予約とだけ重なってよい（2件以上の仮予約にまたがってもよい。第二キープどうしは重ならない）。区間は半開区間 `[start, end)` で扱う | プロパティベーステスト、DB を使う統合テスト（同じ時間への同時の申込で、片方だけが成功する） |
| INV-2 | 枠を確保・解放するすべての操作（申込、承認・却下、昇格、変更、取消、第二キープの繰り上げ・終了、バッファの切り替え、ブロック枠の登録・更新・削除、Googleカレンダーの取り込み）は、枠と予約（またはブロック枠）の書き込みを1トランザクションで行う。途中で失敗したら何も残さない | 統合テスト |
| INV-3 | 公開API（認証なし）が返す空き状況は、時間帯ごとの「空き／第二キープ可／空きなし」の3つの値だけ。予約のID・種類・状態、顧客の個人情報は返さない | 契約テスト（返すキーと値を固定する） |
| INV-4 | 外部から来るデータは境界でパースする（Zod）。パース前のデータを内部に流さない | lint / 型 |
| INV-5 | `apps/api` は `apps/site-*` に依存しない。`apps/site-*` が直接依存できるのは `packages/contracts` と `packages/booking-widget` だけ（`booking-widget` を通した `packages/booking-core` への間接の依存は許す）。`packages/booking-core` は入出力（AWS SDK、HTTP、DB、現在時刻の取得）を持たない | 依存関係lint（dependency-cruiser） |
| INV-6 | 顧客へのメールは、管理者が内容を確認してから送る（自動送信しない）。例外は、申込直後の定型の受付通知だけ。受付通知は人がレビューしたテンプレートを使い、予約の成立・金額・空きの可否を書かない | 仕組み：顧客への送信経路を「管理者が承認した下書きを送る関数」と「受付通知を送る関数（自由な文面を受け取らない）」の2つに限る。lint：SESを呼べるモジュールを1つに限る。統合テスト：承認されていない下書きは送れない |
| INV-7 | 日時はUTCで保存し、表示時にAsia/Tokyoへ変換する。「利用日」「深夜帯」「仮予約の期限」「キャンセル料の日数」などの判定はJSTで行う | 日時ライブラリを1つに限る。現在時刻は時計の部品から取得する（テストで固定できる）。lint：`new Date()`・`Date.now()` の直接呼び出しを禁止する。境界は仕様の例から単体テストにする |
| INV-8 | コストを増やす構成を入れない：VPC内Lambda（NAT Gateway）、Secrets Manager、保存期間なしのログ、常時起動のリソース | Terraformのポリシーチェック |
| INV-9 | 金額は整数（円）で扱い、浮動小数で計算しない。端数の処理は、決めた1か所（税抜で合計 → 消費税10% → 1円未満切り捨て。キャンセル料は 金額 × 率 → 1円未満切り捨て）だけで行う | 金額の型（branded type）、lint、仕様の例からの単体テスト |
| INV-10 | 顧客の個人情報（氏名、会社名、メールアドレス、電話番号、住所、カメラマン氏名、自由記述の欄）を、ログと管理者への通知メールに出さない。通知メールには管理画面へのリンクだけを書く | lint（ロガーに渡せる型を限る）、ログと通知の出力を捕まえて確かめるテスト |

## 自律度

壊れたときの痛さで、エージェントにどこまで任せるかを決める。

| レベル | 対象 | エージェントにできること |
|---|---|---|
| 高 | HP・管理画面の見た目、harness-log・README・実装の説明、自律度「高」の領域のテストの追加、リファクタリング（不変条件に触れないもの） | 実装からPR作成まで。マージは人間（中身の確認は軽くてよい）。当面の扱いで、PRが自律度「中」の領域に触れていないことをCIで判定できるようになったら「マージまで」に戻す |
| 中 | 空き判定、予約の作成・変更・取消、料金・キャンセル料の計算、メール本文とテンプレート（受付通知を含む）、公開APIの契約、Googleカレンダーの取り込み、お知らせ記事、product-specs・core-beliefs・TECH_STACK・TESTING の変更 | 実装とPR作成まで。テスト必須、人間がレビューしてマージ |
| 低 | DBスキーマ・キー設計の変更、本番の `terraform apply`、データの削除・移行、DNS | 変更案（計画とplan結果）の提示まで。実行は人間 |

理由（自律度の見直し）：
- 「高」のマージを当面人間にしているのは、エージェントが使う gh では「高」と「中」のPRを区別できず、マージを許すと「中」のPRもマージできてしまうため（2026-10-12）
- 仕様・不変条件・技術方針は人間が決めるものなので、エージェントは変更をPRにするまで（未決事項への追記と質問も、PRで行う）
- 自律度「中」の領域のテストは、TESTING.md の手順どおり人間がレビューする
- Googleカレンダーの取り込みは間違うと枠を消してしまう。受付通知は自動で送られる。お知らせ記事はお客様が読む。どれも、壊れたときにお客様に影響する

## 技術判断の原則

- **退屈な技術を選ぶ。** 広く使われていて、エージェントが扱い慣れているものを優先する
- 依存パッケージを追加するときは、理由を PR に書く。小さな機能なら自前で書く方を検討する
- 1つのアプリをローカルでも本番でも同じように起動できること。エージェントがワークツリーごとに起動して検証できる状態を保つ

## 人間の役割

- 何を作るか、何を守るかを決めて、このディレクトリに書く
- エージェントが詰まったら「もっと頑張れ」ではなく、足りないもの（情報、ツール、制約）を探してリポジトリに足す
- 自律度「中」「低」の判断をする

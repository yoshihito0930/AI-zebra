# 管理 API

管理画面（apps/admin）が呼ぶ API（apps/api/src/admin）の形。何をできるかは [index.md](../product-specs/index.md) の「予約API」「管理画面」、業務のルールは [booking.md](../product-specs/booking.md)、予約のデータと操作は [reservation-model.md](reservation-model.md)、読み書きは [dynamodb-keys.md](dynamodb-keys.md)。食い違ったら booking.md が正しい。

関連：[core-beliefs.md](core-beliefs.md)（INV-4、INV-6、INV-7、INV-10）、[TECH_STACK.md](../TECH_STACK.md)（認証は Cognito、API の入口は API Gateway HTTP API）

## 作る順

管理 API は大きいので、分けて作る。

1. 予約の一覧・詳細と、承認まわりの操作（承認・却下・昇格・取消・繰り上げ）
2. 2a：保存の層がもうある操作。警告の確認が要る操作（変更・直接入力）と、ブロック枠（入れる・消す・直す）
   2b：保存の層から作る操作。バッファの切り替えと、お客様の情報・撮影の内容の変更
3. 下書きの一覧と送信（INV-6）

この文書は1回目の形を決め、2回目に使う警告の確認の流れも先に決めておく。

## 認証

- 本番（Lambda）：API Gateway の JWT オーソライザーが Cognito のトークンを確かめる。API は、確かめ済みのトークンの `sub` を管理者の id として使う（履歴の「誰が」）。API 自身はトークンを確かめない
- 手元（Node サーバー。server.ts）：環境変数 `DEV_ADMIN_USER_ID` に書いた管理者として動く。Cognito がなくても管理画面を作れるようにするため
- `DEV_ADMIN_USER_ID` を読むのは server.ts だけ。lambda.ts は読まない（本番で仮の管理者が効かないことを、テストで確かめる）
- 管理者の id が取れないときは、どのルートも 401 にする
- 管理者は今は1人。管理者ごとの権限の違いは持たない

## 一覧・詳細（1回目）

### 予約の一覧：`GET /admin/reservations`

- `from`・`to`（JST の日付 YYYY-MM-DD。両端を含む。最長62日）を渡すと、その期間の日にかかる予約とブロック枠を返す。「かかる」は占有区間（バッファを含む）で見る。バッファだけが次の日にかかる予約も、次の日の一覧に出る（日ごとのアイテムの持ち方と同じ）。日ごとのアイテムを読み、出てくる予約の META と、表示する氏名だけのために個人情報を読む
- `status` だけを渡すと、その状態の予約を、期間によらず開始の早い順に返す（承認待ちの一覧など。状態の GSI を読む）。`from`・`to` と一緒に渡すと、期間の中をその状態で絞る
- 一覧に出るのは、枠を確保している予約（承認待ち・仮予約・本予約・第二キープ）とブロック枠だけ。取消・終了の予約は出ない。取消した予約は、受付番号か予約の id で開く
- 予約ごとに返すもの：id、受付番号（フォームの申込だけ）、状態、予約区間、バッファ、経路、人数、見積額（税込）、確定金額、第二キープの仮予約の id、氏名。個人情報のうち一覧に出すのは氏名だけ
- ブロック枠ごとに返すもの：id、区間、バッファ、経路、理由のメモ
- 開始の早い順に並べる（開始が同じなら終わりの早い順、それも同じなら id の順）

理由：一覧で誰の予約かを見分けられるようにする。管理者しか呼ばない API なので、氏名を返してよい（INV-10 はログと通知メールの決まり）。62日は、月ごとのカレンダーで前後の月にまたがる表示もできる長さ。取消・終了を一覧に出すには状態の GSI を変える必要があり、v1 ではしない。

### 予約の詳細：`GET /admin/reservations/{id}`

- 予約の META・個人情報・履歴を返す
- 承認待ちなら、今の料金表で計算し直した見積も返す（承認のときに、申込のときの見積と比べるため。reservation-model.md「金額」）
- 取消できる状態（仮予約・本予約・第二キープ）なら、今取消したときのキャンセル料も返す（取消の前に見せるため）

### 受付番号から探す：`GET /admin/receipts/{受付番号}`

- 予約の id を返す。お客様から受付番号で問い合わせを受けたときに使う
- 受付番号の形（packages/contracts の `ReceiptNumber`）でないときは 400（`invalid-input`）。形は正しいがないときは 404

## 操作（1回目）

| 操作 | ルート | 本文 |
|---|---|---|
| 承認 | `POST /admin/reservations/{id}/approve` | 確定金額（税込） |
| 却下 | `POST /admin/reservations/{id}/reject` | なし |
| 昇格 | `POST /admin/reservations/{id}/promote` | なし |
| 取消 | `POST /admin/reservations/{id}/cancel` | なし |
| 繰り上げ | `POST /admin/reservations/{id}/move-up` | なし |

- 判定と保存は、保存の層の `saveReservationOperation` に任せる。操作の日時は、API の現在時刻（app.ts の `now`。INV-7）
- 成功したら、200 と、作った下書きの一覧（種類、あて先の予約の id、差し込む値）を返す。下書きは送らない（INV-6。送るのは3回目）

## 警告の確認（2回目）

変更と直接入力では、締め切りと、深夜帯にかかる予約の最短4時間が警告になる（booking.md「直接入れる予約のルール」「予約の変更」）。

- 本文に、管理者が確認した警告の一覧（`acknowledgedWarnings`）を付けられる
- API は、そのときの警告を計算し直す。警告がすべて確認済みなら保存する。確認していない警告が1つでもあれば保存せず、409 と、今の警告の一覧を返す
- 管理画面は、1回目は確認なしで送り、409 で返った警告を見せ、管理者が確認したら、その一覧を付けて送り直す

理由：「確認済み」の印だけだと、確認したあとに日時を変えて別の警告が出ても入ってしまう。確認した警告そのものを送り返せば、今の警告と比べられる。

- 警告の種類：`past-24-hours-before-start`（本予約の締め切り）、`past-provisional-deadline`（仮予約・第二キープの締め切り）、`late-night-shorter-than-4-hours`（深夜帯にかかり4時間未満）。名前は公開APIの契約（ApplicationRejection）と同じ
- 確認した一覧に、今は出ていない警告が入っていてもよい（確認のあとに日時を直して、警告が消えた場合）
- 警告より先に、不可の決まり（30分単位、2時間未満、24時間超、空き判定など）を確かめる。不可なら、警告を確認していても保存しない

## 変更・直接入力・ブロック枠（2回目a）

### 予約の変更：`POST /admin/reservations/{id}/change`

- 本文：変更後の予約区間（開始・終わり）、人数、ホリゾントの養生、機材保険、オプション、確定金額（税込）、確認した警告。日時を変えないときも、今の日時を送る（変える欄だけを送る形にはしない）
- 警告は `checkReservationChangeTime`（日時を変えないときは出ない）。操作の日時は API の現在時刻
- 見積は今の料金表で計算し直す（保存の層が履歴に残す）。成功したら 200 と、作った下書きの一覧

### 直接入力：`POST /admin/reservations`

- 本文：種類（仮予約・本予約・第二キープ）、予約区間、人数、ホリゾントの養生、機材保険、オプション、確定金額（税込）、お客様の情報、撮影の内容、確認した警告
- お客様の情報は、氏名と、電話番号かメールアドレスのどちらか1つが必須。ほかは任意。入れた欄の形と長さの上限は申込フォームと同じ（booking.md「直接入れる予約のルール」）。人数の上限は設けない（15人以上は管理者が直接入れる。booking.md「申込フォーム」）
- 警告は `checkDirectEntry` の警告。バッファは初期値の60分
- 見積は今の料金表で計算する。成功したら 201 と、予約の id

### ブロック枠：`POST /admin/blocks`、`PUT /admin/blocks/{id}`、`DELETE /admin/blocks/{id}`

- 入れる・直すの本文：区間（開始・終わり）、バッファ（0・30・60）、理由のメモ（任意）。直すときも全部を送る
- 警告はない（ブロック枠には締め切りも最短時間もない）
- 入れたら 201 とブロック枠の id、直す・消すは 200
- Googleカレンダーから取り込んだブロック枠は、直す・消すと 409（`google-calendar-block`）

## 返すときの決まり

- 日時は ISO 8601 のオフセット付き（JST で表す）。日付は JST の YYYY-MM-DD
- 外から来る本文・クエリは、契約（packages/contracts の Zod スキーマ）でパースする（INV-4）
- エラーは `{ error: <理由> }` で返す

| 状況 | ステータス | 理由 |
|---|---|---|
| 入力の形が正しくない（期間が62日を超える、from が to より後、受付番号の形でない、を含む） | 400 | `invalid-input` |
| 管理者の id が取れない | 401 | `unauthorized` |
| 予約・ブロック枠がない、受付番号がない | 404 | `not-found` |
| 今の状態ではできない操作（承認待ちでない、変更できない状態、など） | 409 | `not-pending`・`invalid-status`・`still-held`・`not-changeable` |
| Googleカレンダーから取り込んだブロック枠を直す・消す | 409 | `google-calendar-block` |
| 確認していない警告がある | 409 | `unacknowledged-warnings`（今の警告の一覧 `warnings` を付ける） |
| 決まりで不可（30分単位、2時間未満、24時間超、空き判定、付く仮予約がない、ブロック枠の90日） | 422 | `not-on-30-minute-boundary`・`shorter-than-2-hours`・`longer-than-24-hours`・`overlaps-existing`・`no-provisional-to-hold`・`more-than-90-days`（公開APIと同じく 422） |
| 混み合っている | 503 | `busy` |

- ログには、エラーの種類だけを出す。本文・個人情報は出さない（INV-10。公開APIと同じ）

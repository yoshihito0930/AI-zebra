# Product Specs — v1

## 誰のためのものか

- **お客様**: スタジオを借りて撮影したい人。HPでスタジオを知り、空き状況を見て予約する
- **スタジオ管理者**: 予約を確認・承認し、お客様に連絡する。利用者は数人。HPの記事も更新する

## v1 のスコープ

予約のルールは [booking.md](booking.md) を参照。

### HP（apps/site-zebra）

- 静的サイト。WordPress のような管理ページ（CMS）は持たない。理由：軽くしたい。記事は管理者が自分で更新するので、管理ページは不要
- お知らせ記事は、リポジトリの Markdown として持つ。管理者が更新し、ビルドして公開する
- URLは今のHP（https://studiozebra-1st.com/ 、WordPress）と同じにする。理由：検索順位やブックマークをそのまま引き継げ、リダイレクトの対応表が要らない
- 予約以外の問い合わせ用のフォームは作らない。メール・電話・LINEの連絡先を載せる

### 予約ウィジェット（packages/booking-widget）

- 日付ごとの空き状況をカレンダーで表示する
- 状態：空きあり / 空きなし / 読み込み中 / エラー
- 時間帯ごとの状態は「空き／第二キープ可／空きなし」の3つ（INV-3）。第二キープ可の時間帯を選んだときは、第二キープとして申込めることを案内する
- 申込フォーム（[booking.md](booking.md) の「申込フォーム」）。入力に応じて見積額を表示する

### 予約API（apps/api）

- 公開：空き状況の取得、予約の申込（第二キープを含む）
- 管理：
  - 予約の一覧・詳細、承認・却下、仮予約の本予約への昇格、変更、取消
  - 第二キープの繰り上げ・取消
  - バッファの1時間／30分の切り替え
  - 金額の調整、キャンセル料の計算
  - 管理者による予約の直接入力、ブロック枠（休業など）の登録
  - Googleカレンダーの取り込み（定期と手動）
  - メールの下書きと送信
- メール：お客様への定型の受付通知（自動）、管理者への新しい申込の通知（自動）

### 管理画面（apps/admin）

- ログイン（スタッフのみ）
- 予約一覧（日付・状態で絞り込み）、詳細、承認・却下・昇格・変更・取消
- 警告の表示：放置された承認待ち、期限を過ぎた仮予約、繰り上げを待っている第二キープ
- 第二キープの繰り上げ・取消、バッファの切り替え、金額の調整、キャンセル料の表示
- 予約の直接入力（電話・メールで受けたもの）、ブロック枠の登録
- Googleカレンダーの「今すぐ取り込む」ボタン、取り込めなかった予定の表示
- メールの下書きを確認してから送信する

理由（予約の直接入力とブロック枠）：電話・メールで受けた予約や休業をシステムに入れられないと、ウィジェットからの申込とダブルブッキングになる。管理者が手で予約を管理できる経路も残したい。

### Googleカレンダーの取り込み（並行稼働のため）

予約受付を始めてからしばらくは、今の運用（Googleカレンダーに予約を入れる）と新しいシステムを並行して動かす。

- Googleカレンダーの予定を、システムのブロック枠として取り込む（Googleカレンダー → システムの一方向）
- 取り込みは1日1回の定期実行と、管理画面の「今すぐ取り込む」ボタン
- 取り込んだブロック枠は、Googleカレンダーに合わせる。予定が動けば更新し、消えれば解放する
- 取り込む予定や移動先が、システム上の予約・ブロック枠と重なるときは、取り込まない（更新しない）。管理画面に表示して、管理者に知らせる
- 予約受付を始める前の既存の予約も、この取り込みで入れる
- v1のあとで、システムの予約をGoogleカレンダーに「予定あり」として書き込む逆向きの流れを入れる予定。そのとき、システムが書いた予定を自分で取り込み直さないように、v1の取り込みは最初から「システムが書いた予定（目印のあるもの）は取り込まない」前提で作る。v1の認証は読み取り専用

理由：並行稼働の間も、今までどおりGoogleカレンダーに入れるだけで、システムの空き状況に反映できるようにするため。1日1回でも、ウィジェットからの申込は必ず承認を通るので、承認の前に「今すぐ取り込む」を押せばダブルブッキングを防げる。

#### 例

| Googleカレンダーの変化 | システムの結果 |
|---|---|
| 予定 10/20 13:00–15:00 を追加 | 次の取り込みで、ブロック枠 10/20 13:00–15:00 を作る |
| その予定を 10/20 17:00–19:00 に移動 | ブロック枠を 17:00–19:00 に更新する。13:00–15:00 は解放する |
| その予定を削除 | ブロック枠を削除し、枠を解放する |
| 予定 10/21 10:00–12:00 を追加。システムに承認待ち 10/21 10:00–12:00 がある | 取り込まない。管理画面に表示して知らせる |
| 予定を、システム上の本予約と同じ時間帯に移動 | 更新しない（元のブロック枠のまま）。管理画面に表示して知らせる |

## v1 でやらないこと

- 複数スタジオ（マルチテナント）対応
- オンライン決済
- AIによるメール文面の自動作成
- お客様のアカウント登録・ログイン（会員とゲストの区別はしない）
- お客様がシステム上で取消・変更すること（電話・メールで受け、管理者が操作する）
- 予約以外の問い合わせフォーム
- HPの管理ページ（CMS）
- ロケハン（下見）の予約（システムの外で扱う）
- 「仮予約は1つの利用日につき2日まで」のシステムでの判定（表示と管理者の確認で扱う）
- システムからGoogleカレンダーへの書き込み（v1のあとで入れる予定）

## リリースの進め方

1. 本番構成に非公開でデプロイし続ける（ベーシック認証など）
2. 新HPを公開する。条件は、デザインが固まり、料金プランの見直しが終わっていること。`/reservation/` には今の仕組み（Googleカレンダーの埋め込みと、form.run の予約フォーム）を載せる
3. Googleカレンダーの取り込みを動かし、既存の予約がブロック枠として入っていることを確認する
4. 期間をあけて、機能フラグで予約ウィジェットを有効にする。Googleカレンダーとの並行稼働を始める
5. 並行稼働を終え、予約の管理をシステムに一本化する

HPの公開と予約受付の開始は同じ日にしない。
